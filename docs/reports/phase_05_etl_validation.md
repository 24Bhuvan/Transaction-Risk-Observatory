# Phase 5 — ETL Validation Report

## 1. ETL Objective

Phase 5 loads the validated staging data into the analytics layer while
preserving source transaction grain, source values, NULL behavior, and
identity relationships.

The Phase 5 ETL follows these principles:

- Staging tables remain source-only and are not modified.
- `analytics.dim_identity` is loaded before `analytics.fact_transaction`.
- `TransactionID` remains the source identifier.
- `identity_key` and `transaction_key` are analytical surrogate keys.
- Transactions without identity records are retained with
  `fact_transaction.identity_key = NULL`.
- The ETL uses a controlled full-refresh batch strategy.
- Validation and reconciliation are performed after loading.

## 5. Fact Load

`analytics.fact_transaction` is loaded from `staging.raw_transactions`
using a `LEFT JOIN` to `analytics.dim_identity` on `TransactionID`.

The `LEFT JOIN` is required so that transactions without identity records
are retained.

`transaction_key` is generated by PostgreSQL and is not supplied by the
ETL INSERT statement.

### ETL Rerun Strategy

Phase 5 uses a controlled full-refresh batch strategy.

The development reload order is:

```text
TRUNCATE fact_transaction
        ↓
TRUNCATE dim_identity
        ↓
LOAD dim_identity
        ↓
LOAD fact_transaction
        ↓
VALIDATE
```

The staging tables are never truncated or modified.

### Transactional ETL Strategy

Where practical, the controlled full-refresh execution should run within a
database transaction:

```text
BEGIN
   ↓
TRUNCATE
   ↓
LOAD dimension
   ↓
LOAD fact
   ↓
VALIDATE
   ↓
COMMIT
```

If a critical operation fails:

```text
ROLLBACK
```

This prevents a partially loaded analytical model.

The `TRUNCATE` and transaction-control statements are documented as the
controlled rerun strategy and are not to be executed blindly against the
currently validated populated target tables.

Incremental ETL logic is out of scope for Phase 5.
