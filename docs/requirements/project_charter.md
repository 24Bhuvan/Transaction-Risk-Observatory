# Transaction Risk Observatory

## 1. Project Overview

Transaction Risk Observatory is a PostgreSQL-centric transaction risk analytics project designed to transform raw IEEE-CIS Fraud Detection data into a structured, validated, and analytically useful fraud-risk environment.

The project focuses on the complete analytical lifecycle:

```text
Raw IEEE-CIS Data
        ↓
PostgreSQL Staging
        ↓
Data Profiling & Quality Assessment
        ↓
Relational / Dimensional Modeling
        ↓
ETL / ELT
        ↓
Cleaning & Transformation
        ↓
Data Quality Validation
        ↓
Fraud-Risk Signal Generation
        ↓
KPI & Business Analysis
        ↓
Analytical Views / Reports
        ↓
Query Optimization & Performance Analysis
        ↓
Monitoring & Documentation
```

The primary analytical engine is PostgreSQL. SQL is used as the principal language for data preparation, transformation, validation, fraud-risk analysis, KPI computation, and performance optimization.

The project is intended as an analytical and engineering portfolio project rather than a production fraud-detection platform.

---

## 2. Problem Statement

Financial transaction datasets can contain complex relationships between transactions, customers, devices, identities, merchants, products, locations, and temporal behavior.

Fraudulent transactions may not be identifiable from a single attribute. Suspicious behavior can emerge from combinations of:

* Transaction amount anomalies
* Transaction velocity
* Repeated activity
* Temporal behavior
* Device activity
* Entity-level behavior
* Geographic inconsistencies
* Changes in transaction attributes
* Multiple simultaneous risk signals

The project addresses the problem of converting raw transaction and identity data into a reliable analytical system capable of identifying and measuring such patterns through transparent, reproducible SQL-based analysis.

The system must also distinguish between:

* Ground-truth fraud labels
* Analytical risk signals
* Composite risk scores
* Business KPIs

A risk score represents analytical evidence generated by defined rules and must not be treated as equivalent to the ground-truth fraud label.

## 3. Project Objective

The primary objective is to build a PostgreSQL-centric transaction risk analytics system that transforms raw IEEE-CIS transaction and identity data into a validated analytical model and derives rule-based fraud-risk signals, KPIs, and investigative outputs using advanced SQL.

The project will demonstrate the ability to:

* Ingest raw transaction and identity data
* Build a controlled PostgreSQL staging layer
* Profile datasets and assess data quality
* Design an appropriate relational and dimensional model
* Perform SQL-based ETL/ELT
* Clean and transform analytical data
* Validate data through reconciliation and quality checks
* Generate deterministic fraud-risk signals
* Develop transparent risk-scoring logic
* Calculate fraud and operational KPIs
* Create analytical views and materialized reporting structures
* Apply indexing and query optimization techniques
* Evaluate query performance using `EXPLAIN` and `EXPLAIN ANALYZE`
* Create repeatable monitoring and validation queries
* Maintain a reproducible, version-controlled analytical workflow

---

## 4. Business Objectives

The project aims to answer practical transaction-risk questions such as:

1. How frequently does fraud occur in the dataset?
2. What transaction value is associated with fraudulent activity?
3. How does fraudulent transaction behavior differ from non-fraudulent behavior?
4. During which time periods does fraudulent activity occur more frequently?
5. Are there transaction bursts or velocity patterns associated with fraud?
6. Which entities or devices exhibit elevated risk patterns?
7. Are unusual transaction amounts associated with fraudulent activity?
8. Are there geographic inconsistencies that may indicate suspicious activity?
9. How frequently do multiple risk signals occur within the same transaction?
10. Can a transparent rule-based risk score help prioritize transactions for investigation?

The project is intended to support analytical investigation and prioritization rather than automatically determine whether a real-world transaction should be blocked.

## 8. Key Analytical Questions

### Fraud Exposure

**AQ01 — Fraud Rate**

What percentage of eligible transactions are fraudulent?

**AQ02 — Fraud Transaction Value**

What transaction value is associated with fraudulent transactions?

**AQ03 — Fraud vs Non-Fraud Amount**

How do average transaction amounts differ between fraudulent and non-fraudulent transactions?

### Temporal Behavior

**AQ04 — Fraud by Time**

How does fraud activity vary across relevant time periods?

**AQ05 — Transaction Bursts**

Are unusually dense transaction sequences associated with fraudulent activity?

**AQ06 — Pre-Fraud Transaction Frequency**

Does transaction frequency increase before transactions labeled as fraudulent?

### Transaction Behavior

**AQ07 — Amount Anomalies**

Which unusual transaction amounts are associated with elevated fraud incidence?

**AQ08 — Recurring Transaction Patterns**

Are repeated or recurring transaction patterns associated with suspicious behavior?

### Entity and Device Behavior

**AQ09 — High-Risk Entities**

Which identifiable entities demonstrate elevated fraud or risk-signal rates?

**AQ10 — Device Risk**

Which devices or device-related attributes demonstrate elevated risk patterns?

**AQ11 — Attribute Changes**

Are changes in relevant transaction or identity attributes associated with suspicious behavior?

### Geographic Behavior

**AQ12 — Geographic Inconsistency**

Are geographically inconsistent transaction patterns associated with fraud?

**AQ13 — Implausible Movement**

Where applicable, do transaction sequences imply implausible geographic movement within the available data?

### Risk Scoring

**AQ14 — Multiple Risk Signals**

How frequently do transactions trigger multiple independent risk signals?

**AQ15 — Transparent Risk Score**

Can multiple deterministic risk signals be combined into a transparent composite risk score for analytical prioritization?

## 9. KPI Framework

The KPI framework will be finalized after dataset profiling and confirmation of the available fields.

Core KPIs include:

| KPI                          | Definition                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------ |
| Fraud Rate                   | Fraudulent transactions divided by eligible transactions                       |
| Fraud Count                  | Count of transactions where `isFraud = 1`                                      |
| Non-Fraud Count              | Count of transactions where `isFraud = 0`                                      |
| Total Transaction Amount     | Sum of the confirmed transaction amount field                                  |
| Fraud Amount                 | Sum of the confirmed transaction amount field for fraudulent transactions      |
| Average Transaction Amount   | Average transaction amount across eligible transactions                        |
| Average Fraud Amount         | Average transaction amount for fraudulent transactions                         |
| Risk Signal Count            | Number of deterministic risk signals triggered                                 |
| Risk Signal Rate             | Transactions triggering a defined risk signal divided by eligible transactions |
| Multi-Signal Count           | Transactions triggering at least two risk signals                              |
| Multi-Signal Rate            | Multi-signal transactions divided by eligible transactions                     |
| Average Risk Score           | Average deterministic composite risk score                                     |
| High-Risk Count              | Transactions exceeding the defined high-risk threshold                         |
| High-Risk Rate               | High-risk transactions divided by eligible transactions                        |
| Fraud Rate by Entity         | Fraud rate grouped by the selected entity                                      |
| Fraud Rate by Device         | Fraud rate grouped by the selected device attribute                            |
| Fraud Amount Share           | Fraud amount divided by total transaction amount                               |
| Transactions per Time Window | Transaction count within a defined time period                                 |
| Velocity Signal Rate         | Rate of transactions triggering the defined velocity rule                      |
| Geographic Anomaly Rate      | Rate of transactions triggering a geographic anomaly rule                      |
| Amount Anomaly Rate          | Rate of transactions triggering an amount-anomaly rule                         |

### KPI Conventions

The project uses the following principles:

* `isFraud = 1` represents the ground-truth fraudulent class.
* `isFraud = 0` represents the ground-truth non-fraudulent class.
* Every rate must explicitly define its denominator.
* Every time-based KPI must define its time grain.
* The final transaction amount field will be confirmed from the dataset schema before production KPI queries are created.
* Risk scores are analytical constructs and are not ground-truth fraud labels.
* Risk signals are deterministic SQL rules.
* Multi-signal activity is defined as a transaction triggering at least two independent risk signals unless later analysis establishes a different justified threshold.

## 14. Project Constraints

The project operates under the following constraints:

1. PostgreSQL is the primary analytical platform.
2. SQL is the primary implementation language.
3. The project uses the IEEE-CIS Fraud Detection dataset.
4. Fraud analysis is rule-based and deterministic.
5. Machine learning is outside the project scope.
6. The project does not implement real-time transaction authorization.
7. The project does not automatically block transactions.
8. Risk scores must remain distinguishable from ground-truth fraud labels.
9. Final analytical rules must be based on the actual dataset structure and validated evidence.
10. KPI definitions must explicitly specify their numerator, denominator, and time grain where applicable.
11. Performance optimization must be supported by measurable PostgreSQL execution evidence.
12. Raw source data should remain separate from transformed analytical data.
13. Reproducibility is required through version-controlled SQL scripts and documentation.
14. Final tables and analytical structures will be created progressively across later project phases rather than prematurely during Phase 1.
