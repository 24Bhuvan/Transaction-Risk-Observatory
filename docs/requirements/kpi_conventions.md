# Transaction Risk Observatory — KPI Conventions

## 1. Purpose

This document establishes consistent definitions and calculation conventions for fraud-related KPIs and analytical risk metrics.

These conventions must be followed throughout the project to prevent inconsistencies between SQL queries, analytical views, reports, and documented results.

---

## 2. Fraud Definition

The IEEE-CIS source dataset's fraud label is treated as the ground-truth transaction classification.

```text
isFraud = 1 → Ground-truth fraudulent transaction
isFraud = 0 → Ground-truth non-fraudulent transaction
```

The source fraud label must not be modified during analytical processing.

Any SQL-generated fraud-risk indicator is considered an analytical signal and must remain distinct from the source `isFraud` label.

---

## 3. Fraud Rate

Fraud Rate measures the proportion of eligible transactions that are labeled fraudulent by the source dataset.

### Formula

```text
Fraud Rate =
Number of transactions where isFraud = 1
/
Number of eligible transactions
```

Equivalent SQL concept:

```sql
COUNT(*) FILTER (WHERE is_fraud = 1)
/
COUNT(*)
```

The denominator must represent the same eligible transaction population as the numerator.

Fraud Rate must be reported as a percentage when presented as a KPI.

---

## 4. Fraud Count

Fraud Count represents the number of transactions labeled fraudulent by the source dataset.

### Formula

```text
Fraud Count =
COUNT(transactions WHERE isFraud = 1)
```

This metric must not include transactions that are merely flagged by an analytical risk rule.

---

## 5. Transaction Amount Convention

The project will identify and formally designate the appropriate transaction amount field after the IEEE-CIS dataset structure is confirmed.

The selected field must represent the transaction monetary amount relevant to the project's analytical objective.

Until the dataset is profiled and the field is confirmed:

* No amount column will be permanently designated as the project's transaction amount.
* No final fraud-amount KPI will be claimed.
* The selected amount field will be documented with its source column name and business meaning.
* All monetary KPIs will use the same approved amount field unless a different financial concept is explicitly documented.

### Important Distinction

A metric must not be called **Fraud Amount** if the underlying column represents a different financial concept.

For example, transaction amount, payment amount, authorized amount, settled amount, and loss amount are not automatically interchangeable.

---

## 6. Fraud Amount

Fraud Amount represents the sum of the approved transaction amount field for transactions labeled fraudulent.

### Formula

```text
Fraud Amount =
SUM(transaction_amount WHERE isFraud = 1)
```

The exact source column used for `transaction_amount` will be finalized after dataset profiling.

Fraud Amount represents the transaction value associated with ground-truth fraudulent transactions.

It does not automatically represent:

* Confirmed financial loss
* Recovered funds
* Chargeback amount
* Customer loss
* Bank loss
* Net fraud exposure

Those concepts require separate source fields and definitions.

---

## 7. Average Fraud Amount

Average Fraud Amount represents the mean transaction amount among transactions labeled fraudulent.

### Formula

```text
Average Fraud Amount =
SUM(transaction_amount WHERE isFraud = 1)
/
COUNT(transactions WHERE isFraud = 1)
```

Equivalent analytical concept:

```sql
AVG(transaction_amount) FILTER (WHERE is_fraud = 1)
```

The calculation uses the same approved transaction amount field defined in the Transaction Amount Convention.

---

## 8. Risk Signals

Risk signals are analytical indicators generated by deterministic SQL rules.

Examples include:

* High transaction velocity
* Unusual transaction amount
* Off-hours activity
* Geographic inconsistency
* Device-related anomaly
* Entity-related anomaly
* Multiple suspicious attributes occurring together

Each risk signal must have:

1. A unique name.
2. A documented business definition.
3. A deterministic SQL rule.
4. A defined threshold where applicable.
5. A boolean or equivalent indicator.
6. A documented analytical grain.

---

## 9. Risk Score

The risk score is an analytical measure derived from rule-based risk signals.

### Core Principle

```text
Risk Score ≠ Ground-Truth Fraud Label
```

The risk score does **not** replace or modify `isFraud`.

The source label answers:

> Was this transaction labeled fraudulent in the dataset?

The risk score answers:

> How many or how strongly did the defined analytical risk signals trigger for this transaction?

---

## 10. Risk Score Construction

The initial scoring framework may represent the number of triggered independent risk signals.

Conceptually:

```text
Risk Score =
Velocity Signal
+ Amount Signal
+ Temporal Signal
+ Geographic Signal
+ Device Signal
+ Entity Signal
```

For binary signals:

```text
Triggered signal = 1
Not triggered = 0
```

The final signal set and any weighting scheme will be determined after dataset profiling and analytical validation.

If weighted scoring is introduced, the weights must be explicitly documented.

---

## 11. Risk Score Interpretation

A higher risk score indicates that more defined analytical risk conditions were triggered.

It does **not** establish that a transaction is fraudulent.

For example:

```text
isFraud = 1, risk_score = 0
```

means the transaction is labeled fraudulent by the dataset but did not trigger the implemented analytical signals.

And:

```text
isFraud = 0, risk_score = 4
```

means the transaction is labeled non-fraudulent but triggered four analytical risk signals.

These outcomes are analytically valid and must not be overwritten or reclassified.

---

## 12. Multi-Signal Transactions

A multi-signal transaction is one that triggers at least two independent analytical risk signals.

### Definition

```text
multi_signal = risk_signal_count >= 2
```

### Multi-Signal Rate

```text
Multi-Signal Rate =
Number of transactions where risk_signal_count >= 2
/
Number of eligible transactions
```

This metric describes analytical signal behavior, not ground-truth fraud prevalence.

---

## 13. Risk Signal vs. Fraud Label

The following distinction must remain consistent throughout the project:

| Concept                  | Meaning                                                         |
| ------------------------ | --------------------------------------------------------------- |
| `isFraud = 1`            | Source dataset's ground-truth fraud label                       |
| `isFraud = 0`            | Source dataset's ground-truth non-fraud label                   |
| Risk Signal              | Analytical rule triggered by transaction/entity characteristics |
| Risk Score               | Number or weighted strength of triggered analytical signals     |
| Multi-Signal Transaction | Transaction triggering at least two analytical signals          |

A risk signal must never be described as confirmed fraud solely because the rule triggered.

---

## 14. Population and Denominator Convention

Every rate must explicitly define its denominator.

Unless otherwise documented:

```text
Rate =
Relevant transactions
/
Eligible transactions
```

When a rule applies only to a subset of transactions, the eligible population must be documented.

For example, a geographic anomaly rate may use only transactions with sufficient location information rather than all transactions.

---

## 15. Time-Based KPI Convention

Time-based KPIs must explicitly state their temporal grain.

Supported grains may include:

* Hour
* Day
* Week
* Month

The chosen timestamp field and timezone treatment must be documented before final time-based KPI calculations are produced.

---

## 16. Finalization Rule

These conventions establish the project's analytical standards, but fields dependent on the actual IEEE-CIS schema remain provisional until dataset profiling is completed.

Before final KPI reporting:

1. Confirm the fraud label field.
2. Confirm the transaction amount field.
3. Confirm timestamp fields.
4. Confirm available entity and device fields.
5. Confirm geographic fields.
6. Confirm eligible populations for each metric.
7. Document any exclusions or filtering rules.
8. Validate KPI calculations against the source data.

All final KPI SQL must conform to these conventions.
